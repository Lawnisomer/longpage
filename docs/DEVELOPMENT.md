# 开发记录

本记录整理于 2026-10-23，基于实际实现、设备验证和用户反馈。首次 Git 提交是公开整理后的完整快照；下面的阶段不是虚构的历史提交。

## 起点：让一个小工具完成一件事

最初需求是为单台 Android 手机制作长截图工具。范围逐步收敛为竖向连续页面：自己选区、自动滚动、可靠拼接、保存长图。功能简洁、减少错误和改善流畅度始终是优先项。

界面选用 Java 原生 View，构建直接调用 Android SDK 工具。这样能把第一版的依赖压到较低水平，也让截图与滚动逻辑更容易追踪。代价是项目需要自行维护构建脚本，目前只验证了 Windows 构建环境。

## 第一阶段：跑通完整链路

实现了无障碍授权引导、窗口截图、比例选区、自动向下滚动、重叠匹配、暂停结束，以及相册导出。

为了避免整张超高 Bitmap 占用过多内存，采集结果采用磁盘 PNG 条带；导出时一次解码一块并逐行写 PNG。为避免拼进控制按钮，使用目标窗口截图。接缝不可靠时暂停，已经保存的部分仍然可导出。

### 如何知道拼得是否正确

内置测试页使用固定 720px 高的编号面板，每块有不同颜色与图形。除了人工观察，还沿图像边缘统计色块高度，检查跨接缝是否重复或丢行。

基础会话输出 `1220 × 34362`、28 块图像，其中 46 个完整面板保持 720px。导出 PNG 与源条带经色彩空间统一后，单通道最大差为 1。相关合成样本随仓库提供，校验可离线重跑。

## 第二阶段：根据真实使用反馈优化速度

用户自行完成 `1220 × 114284` 长图采集及完整 PNG 导出，证明第一版已经能完成较长任务，同时反馈自动采集过慢。会话索引确认 146 帧；原图和目标页面未公开。

瓶颈不是仅靠优化匹配循环就能解决：每轮手势和固定等待较长，新增内容较少。于是将拖动距离从选区的 34% 增大至约 60%，减少手势与固定等待耗时，同时保留稳定检查和不确定接缝的暂停机制。

### 一个反直觉的发现

直接缩短拖动并静止停留，会导致某些滚动实现保留速度，产生惯性，反而需要更多轮稳定检查。一版短测还出现接缝不确定，因此没有采用该策略。

最终改为快速拖动后，用 180ms 极慢移动约 1px 再抬起，帮助目标界面感知减速。有效对照中，新版每轮中位耗时约 1.55 秒；旧参数在同一编号页约 3.26 秒。按总新增高度计算，采集吞吐从 368.98px/s 提高到 897.92px/s，约 2.43 倍。

这是短合成页面的受控对照，不是所有真实页面的速度保证。加载速度、图像纹理和 PNG 压缩成本都会改变结果。

## 第三阶段：让界面表达更自然

使用说明收短为“打开想要留存的竖向长页。”，去掉限定具体使用对象的表达。

图标采用黑白几何：纵向纸页与取景边角，纸页中的线条透明镂空。桌面、系统应用信息和快捷设置入口统一使用这一造型，并为系统主题提供单色层。圆形、圆角方形及小尺寸效果经过检查。

## 首次公开整理

- 统一项目名称为“长页 / LongPage”，保留现有包名和导出目录以兼容原有安装。
- 将本机绝对路径改为构建参数和环境变量，增加独立临时目录，避免旧编译产物残留。
- 整理 README、架构、构建、隐私、验证、版本与贡献文档，并采用 MIT 许可证。
- 保留合成测试材料与匿名化汇总数据，排除本机签名、真实截图、原始日志、设备标识和私人会话文件。
- 加入 GitHub Actions，持续检查源码构建、匹配算法和离线合成样本。

## 接下来值得改进的方向

优先根据可复现问题改进采集稳定性、内存测量和文档。跨设备兼容、动态布局和加载恢复需要更多明确证据；不把资源保护阈值写成已经验证的极限能力，也不因添加功能而扩大未经验证的承诺。
